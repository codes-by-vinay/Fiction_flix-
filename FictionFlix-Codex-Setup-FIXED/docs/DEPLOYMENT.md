# Deploy FictionFlix

The React site and Flask API should be deployed together on one origin. This keeps the Flask session cookie available to account, profile, and Studio requests without third-party-cookie or cross-origin configuration.

## Render deployment

1. Put the project in a Git repository and connect that repository to Render. The repository root must contain `render.yaml`, `app.py`, and `requirements.txt`.
2. In Render, create the service from the Blueprint. It builds the Vite frontend, starts Flask with Gunicorn, and mounts a persistent disk at `/var/data`.
3. Set `OWNER_EMAIL` to the email address that will own the Studio and set a long, random `OWNER_SETUP_TOKEN` in Render before creating that account. Create the account with the exact owner email and enter the setup token in the signup form. The token is checked by Flask and is never included in the public frontend build. If the owner account already exists, sign in with it, visit `/admin`, and use the one-time owner setup form. Only the configured owner email can claim the first owner role; remove `OWNER_SETUP_TOKEN` from Render after owner access is set up.
4. Wait for the deploy health check and open the generated `onrender.com` URL.
5. Create an account, sign in, and check the story catalogue, profile, and Studio. Use Studio → Team to grant `member`, `team`, or `admin` roles to existing accounts. Admins can manage any supported role from `/dashboard/admin`.

The Flask secret is generated by Render. Do not replace it with a checked-in value. The blueprint stores SQLite data and uploaded artwork on the persistent disk; do not remove that disk or the user/content data will be lost. A Render account and permission to create the service are required to publish the site.

## Local setup

From the workspace root in PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Set-Location .\FictionFlix-Codex-Setup-FIXED
npm ci
npm run build
Set-Location ..
.\.venv\Scripts\python.exe .\app.py
```

Open <http://127.0.0.1:5000>. To create a local Studio owner, set `OWNER_EMAIL` and a private `OWNER_SETUP_TOKEN`, then enter that token during signup or in the `/admin` owner setup form. A production deployment must set `APP_ENV=production` and a stable, private `FLASK_SECRET_KEY`.

## Email verification and password reset

New sign-ups are not activated until the user follows the verification link sent to their email. Configure SMTP before opening registration; verification links expire after 24 hours. Unverified users can request another verification email from the sign-in form. If SMTP is unavailable during sign-up, the pending account is retained and the UI reports that email delivery needs attention.

Password-reset links also use this SMTP configuration. Set `MAIL_SERVER`, `MAIL_PORT`, and `MAIL_DEFAULT_SENDER`. If the provider requires authentication, also set `MAIL_USERNAME` and `MAIL_PASSWORD`; set `MAIL_USE_TLS=true` for STARTTLS or `MAIL_USE_SSL=true` for implicit TLS. Set `PUBLIC_URL` to the public HTTPS site URL when the service is behind a proxy or uses a custom domain; otherwise `RENDER_EXTERNAL_URL` or the request URL is used.

## Existing accounts and local data

The existing SQLite `users` table is migrated in place to add roles, account preferences, and email verification status. Existing accounts are kept verified during migration; new accounts must verify their email. Existing accounts keep the name stored at signup; no Google/Gmail profile data is imported by the email/password sign-in. If this is the first Render deployment, local account records are not automatically copied to Render; users will need to register on the hosted site. Existing browser-only Studio edits can be loaded by signing in as the owner in the same browser, then checking that the server has saved the content before clearing browser data.

## Role-based access

The supported roles are `user`, `member`, `team`, `owner`, and `admin`; public signups default to `user`. Flask session cookies authenticate requests, while the backend reads the current role from SQLite or MongoDB for every protected dashboard/API request. Frontend links are role-filtered, but the backend independently enforces these dashboard permissions: member is available to member/owner/admin; team to team/owner/admin; owner to owner/admin; and admin to admin only. Owners can provision admins through Studio so a first admin can be assigned; `/api/admin/update-role` is reserved for admins.
